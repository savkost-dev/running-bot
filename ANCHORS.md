# ANCHORS — якоря зон и приоритеты «вручную / из систем»

Составлено 29.09.2026 по коду версии 0.32.4 и базе на сервере. Это описание того, что код делает
фактически. Решения, которые приняты, но не реализованы, вынесены в отдельный раздел в конце.

При правке любого из перечисленных мест обновлять этот файл в той же задаче.

---

## 1. Термины

- **Якорь** — значение, от которого считаются темповые зоны пользователя: VO2max или лактатный порог (ЛП).
- **VDOT** — индекс формы по Дэниелсу. Зоны строятся только из него (`zones._zones_from_vdot`).
- **`K_VO2MAX = 0.93`** (`zones.py`) — перевод VO2max в VDOT: `VDOT = VO2max × 0.93`. Временная константа с 05.08.2026.
- **Приоритет** — выбор пользователя, какое значение использовать: `manual` («вручную», 📌) или `device` («из систем», 📡).
- **Запасное значение** — значение второй очереди, которое подставляется, когда выбранного по приоритету нет.

---

## 2. Где лежит (таблица `user_profile`)

| Поле | Что хранит |
|---|---|
| `vo2max_device`, `vo2max_device_source`, `vo2max_device_at` | VO2max с трекера, источник (`garmin` / `coros` / `coros_mcp` / `polar`), дата записи |
| `vo2max_manual`, `vo2max_manual_at` | VO2max, введённый руками или посчитанный из забега |
| `vo2max_manual_note` | пометка «21,1 км за 2:01:34», если ручное значение получено из забега; иначе NULL (с 0.32.0) |
| `vo2max_priority` | `manual` / `device`; пусто = `device` |
| `lt_pace_device`, `lt_hr_device`, `lt_device_source`, `lt_device_at` | порог с трекера |
| `lt_pace_manual`, `lt_hr_manual`, `lt_manual_at` | порог, введённый руками |
| `lt_priority` | `manual` / `device`; пусто = `device` |
| `vo2max`, `vo2max_source`, `vo2max_updated_at`, `lactate_threshold_pace`, `lactate_threshold_hr`, `lactate_source` | **старая схема.** Пишутся до сих пор, но при чтении перекрываются значениями из новой |
| `vo2max_locked`, `lactate_locked` | **замки старой схемы**, см. раздел 8 |

Зоны лежат отдельно: `athlete_cache.pace_zones_json`, `zones_source`, `zones_updated_at`.

## 3. Кто пишет

### Значения с трекера

| Событие | Где | VO2max | Порог |
|---|---|---|---|
| Подключение Garmin (обычное) | `bot.py`, `text_handler`, ветка `awaiting_garmin` | да | да |
| Подключение Garmin (двухфакторка) | `garmin.apply_profile_after_connect` | да | да |
| Подключение COROS старого (пароль) | `bot.py`, `text_handler`, ветка `awaiting_coros` | да | нет |
| Подключение Polar | `oauth_server._notify_polar` | да | нет |
| Подключение COROS нового (без пароля) | `oauth_server._notify_coros` | да (с 0.32.1) | нет |
| Кнопка «обновить данные» | `bot.py`, `button_handler` | Garmin, COROS старый, Polar | только Garmin |
| Ночной опрос 03:45 UTC | `bot.scheduled_cache_refresh` → `fitness._get_vo2max_from_tracker` | первый найденный: Garmin → COROS новый → COROS старый → Polar | нет |
| Плановое обновление 03:00 UTC | `bot.scheduled_data_refresh` | Garmin, если значению больше 7 дней | Garmin |

Функции записи: `database.save_vo2max_device`, `database.save_lt_device`. Пишут всегда, без условий и замков.
Приоритет они не трогают.

### Значения вручную

| Событие | Где | Что пишет |
|---|---|---|
| Кнопка «📊 Указать VO2max» | `text_handler`, `awaiting_profile == "set_vo2max"` | `save_vo2max_manual(value)`, пометка стирается |
| Кнопка «🏁 Пороги из результатов забега» | та же ветка, `awaiting_profile == "set_race_time"` | `save_vo2max_manual(VDOT / K_VO2MAX, note=...)` |
| Кнопка «🏃 Лактатный порог» | `text_handler`, `set_lactate_pace` и `set_lactate_hr` | `save_lt_manual`, два шага: темп, потом пульс |

**Любой ручной ввод ставит приоритет `manual`.** Это заложено в `save_vo2max_manual` и `save_lt_manual`:
явный ввод означает «используй моё».

## 4. Что меняет приоритет

| Событие | VO2max | Порог | Пересчёт зон |
|---|---|---|---|
| Ручной ввод VO2max или забега | → `manual` | не меняется | да |
| Ручной ввод порога | не меняется | → `manual` | да |
| Кнопка «📌/📡 VO2max» в профиле | переключается | не меняется | да (с 0.32.0) |
| Кнопка «📌/📡 ЛП» в профиле | не меняется | переключается | да (с 0.32.0) |
| **Первое** подключение любого сервиса | → `device` | → `device` | нет |
| Обновление токена, повторное подключение | не меняется | не меняется | нет |

Первое подключение определяется в `database.save_token`: токена этого сервиса у пользователя раньше не было
(решение 15.09.2026). Срабатывает для любого сервиса, включая Strava и Whoop, которые VO2max и порог не дают.

## 5. Как читается

Единая точка чтения — `database.get_user_profile`. Она вызывает `get_vo2max_resolved` и `get_lt_resolved`
и перекрывает поля старой схемы.

Правило в обеих функциях одно:
1. берётся значение по приоритету;
2. если его нет, подставляется второе (запасное);
3. если нет обоих, возвращается None.

В профиль попадают `vo2max`, `vo2max_source`, `vo2max_resolved`, `lactate_threshold_pace`, `lactate_threshold_hr`,
`lactate_source`, `lt_resolved`.

### Несимметричность, которую надо помнить

| Случай | Порог | VO2max |
|---|---|---|
| Приоритет `device`, с трекера пусто, подставлено ручное | `lactate_source = "запасной"` | `vo2max_source = "manual"` |

Для порога запасное ручное значение помечается отдельно и в лесенке идёт последним (правка 17.09.2026).
Для VO2max такой пометки нет: запасной ручной VO2max выглядит как прямое указание пользователя.

## 6. Лесенка зон (`zones.resolve_anchor`)

Порядок, первый сработавший побеждает:

1. Порог вручную (`lactate_source == "manual"`) → VDOT из порога.
2. VO2max вручную (`vo2max_source == "manual"`) → `VO2max × 0.93`.
3. VO2max с трекера → `VO2max × 0.93`.
4. Порог с трекера или запасной → VDOT из порога.
5. Ничего нет → прогнозы забегов Strava по Риегелю (`calculate_pace_zones`).

Следствия:
- Если задан ручной порог с приоритетом «вручную», VO2max в расчёте не участвует вообще.
- Порог с трекера используется, только когда VO2max нет никакого.
- У Garmin есть и VO2max, и порог. Якорем служит VO2max, порог справочный. В профиле под ним
  выводится «в расчёте не участвует».

## 7. Пересчёт зон

Зоны считает только `zones.recalculate_and_save`, результат кладётся в `athlete_cache`.
`zones.get_pace_zones` отдаёт кэш как есть и считает заново, только если кэша нет.

Вызывается:
- после ручного ввода VO2max, забега, порога;
- после переключения приоритета кнопками в профиле (с 0.32.0);
- при подключении Garmin, COROS старого, COROS нового (с 0.32.1), Polar, если пришли данные;
- ночью в `scheduled_cache_refresh`, для всех пользователей;
- в `scheduled_data_refresh` после обновления Garmin.

Не вызывается при первом подключении сервиса, когда приоритет переключается в `save_token`.
До ночного пересчёта в кэше остаются зоны от прежнего якоря.

Строка «Источник» в профиле считается на лету через `resolve_anchor`, темпы берутся из кэша.
Если они расходятся, значит после смены якоря не было пересчёта.

## 8. Замки старой схемы

`vo2max_locked` и `lactate_locked` защищают от перезаписи только поля старой схемы (`save_user_profile`).
На якорь они не влияют: значения с трекера пишутся всегда, а чтение идёт через приоритет.

В коде версии 0.32.0 эти поля нигде не выставляются. Значение 1 осталось у части пользователей с прежних версий.
В профиле `lactate_locked` показывается значком 🔒.

Рабочий механизм «не трогай моё значение» — приоритет `manual`.

## 11. Открытые задачи

### 11.0. Принципы (админ, 29.09.2026) и где код им не следует

1. **Писать всё**, что отдаёт сервис.
2. **Приводить к одному формату.**
3. **Стратегия выбирает**, что и когда использовать.

То же записано в `DATA_NORMALIZER_SPEC.md`: «Нормализатор собирает и хранит всё. Приоритизация — отдельный вопрос».

**Целевая схема (админ, 29.09.2026):**

```
сервисы → загрузка (сырой ответ) → единый слой (один формат, у каждого значения источник и дата)
        → рекомендация и расчёт зон читают ТОЛЬКО единый слой
```

Рекомендация не обращается к сервисам напрямую и не содержит веток «если Garmin… если COROS…».
Новый сервис подключается в двух местах: загрузка и перевод в единый формат.

**Как сейчас (0.32.3):** рекомендация единый слой не читает. `bot.send_recommendation` и `recovery.py`
ходят в сервисы напрямую по очереди Garmin → старый COROS → Polar → Strava. Нового COROS в этой очереди нет,
поэтому его данные в рекомендации не попадают ни у кого (проверено по журналу за 26–29.09).

**Чего не хватает единому слою, чтобы рекомендация могла читать только его:**
1. Источник записан один на всю запись (`sources`), а не у каждого значения.
2. Хранится только значение победившего сервиса; значения остальных сервисов отбрасываются при слиянии.
3. Нет прогнозов забегов и последнего старта, они лежат отдельно в `athlete_cache`.

**Старый COROS** удаляется целиком после перевода рекомендации на единый слой. До этого удалять нельзя:
шестеро получают данные для рекомендаций только через него.

Состояние на 0.32.2:

| Слой | Что есть | Следует принципам |
|---|---|---|
| Сырьё, `raw_service_data` | ответы сервисов целиком | да; у COROS нового обновляется нерегулярно (11.3) |
| Единый формат, `unified_cache` | VO2max, порог, восстановление в полях `s3_*` | частично: при слиянии остаётся один источник по порядку Garmin → COROS новый → COROS старый → Polar → Strava, значения остальных теряются |
| Якоря, `user_profile` | VO2max и порог с трекера | **нет** |
| Стратегия, `zones.resolve_anchor` | лесенка из четырёх шагов | частично: не знает источник, одинакова для всех трекеров |

Главное расхождение — якоря. Они не читают единый формат. Их пишут отдельные куски кода в десяти местах
(раздел 3), и каждый сам решает, что писать. Решение «порог COROS не писать» зашито в место записи,
то есть стратегия применена при сборе, а не при использовании.

Вторая причина потерь: в `user_profile` одна ячейка на VO2max с трекера и одна на порог. У пользователя
с двумя трекерами значения второго хранить негде.

### 11.1. Загрузка при подключении — закрыто в 0.32.1
До 0.32.1 `oauth_server._notify_coros` только отправляла сообщения, данные приходили ночным опросом.
Пользователь видел прежний профиль и вводил числа руками, чем возвращал приоритет «вручную».

Правило: **подключение любого сервиса должно сразу обновлять профиль и показывать, что загружено.**

Двое подключились 29.09 до исправления и ввели значения руками. Сравнение с часами в тот же день:
- uid 68: порог и VO2max вручную совпали с часами (4:45 и 46.0). По решению админа переведена на «из систем»
  по обоим приоритетам, VO2max 46.0 записан в `vo2max_device`. ПАНО 4:45 → 4:49. Проверка на семи тренировках:
  группа та же в шести, в одной сместилась на соседнюю при почти равных оценках.
- uid 140: порог совпал с часами (3:57), VO2max введён 56.6 при 53.0 на часах. Правка осознанная, приоритет
  «вручную» оставлен.
Whoop при подключении ничего не загружает; в якоря он не пишет, пустым до утра остаётся только блок восстановления.

### 11.2. Решение от 18.09: якорь COROS нового — порог
Источник: `Threshold Pace` из `queryFitnessAssessmentOverview` (`coros_mcp.parse_fitness`, поле `threshold_pace_sec`).
Писать в `lt_pace_device` с источником `coros_mcp`. VO2max COROS в `vo2max_device` не писать.

Проверка 29.09 по семи пользователям: порог с часов совпадает с ручным вводом с точностью до 3 секунд,
VO2max COROS × 0.93 даёт VDOT на 4–7 пунктов ниже.

Чтобы решение заработало, нужно одновременно:
1. Изменить лесенку: порог с трекера должен идти раньше запасного ручного VO2max (см. несимметричность в разделе 5).
2. Очистить `vo2max_device` у записей с источником `coros_mcp`, иначе старое значение останется якорем.
3. Перевести ночную ветку `coros_mcp` в `fitness._get_vo2max_from_tracker` с VO2max на порог.

### 11.5. Устаревшие данные выдаются за свежие (найдено 29.09, не исправлено)

Проверено на промпте шага 2 для uid 122 (`/p_b_user`): в промпт ушла «готовность 65/100 (coros-calc)»,
посчитанная из ответа старого COROS от 06.09 и нового от 17.09. Старый COROS у пользователя отключён.

Причины:
- при отключении сервиса его строка в `raw_service_data` не удаляется;
- `data_normalizer.run_normalization` читает все строки подряд, не глядя ни на наличие токена, ни на возраст;
- ночью единый слой пересобирается и получает сегодняшнюю `updated_at`;
- проверка свежести `get_unified_data(max_age_hours=20)` смотрит на `updated_at`, то есть на дату сборки,
  а не на дату данных.

### 11.6. Новый COROS не участвовал в очередях рекомендации — закрыто в 0.32.4

`fitness.get_coros_fitness_data` и ветка COROS в `recovery._get_recovery_data` обращаются только к старому COROS.
По журналу за 26–29.09: у пользователей только с новым COROS источник данных «profile_only» или «нет данных».
Решение админа: сначала доделать существующую схему, то есть поставить новый COROS в эти очереди,
и только потом менять устройство.

### 11.4. Подписи в профиле у пользователей COROS — закрыто в 0.32.2
Названия источников для показа берутся из `zones.SOURCE_LABELS`. При добавлении нового трекера дописать его туда
и в список источников в `bot._vo2max_tag`.

Было замечено 29.09 на профиле uid 68 после перевода на «из систем»:
- `VO2max: 46.0 (вручную)` — значение с часов. `bot._vo2max_tag` знает только источники `garmin` и `manual`,
  всё остальное подписывает «вручную».
- `Лактатный порог: 4:45 (из сервиса)` — значение ручное, подставлено запасным. Подпись строится по правилу
  «не manual, значит из сервиса», а источник у запасного — «запасной».
- `Источник: VO2max 46.0 (coros_mcp)` — пользователю показывается техническое имя источника.

Подписи перепутаны относительно факта. На расчёт не влияет, но сбивает пользователя.

### 11.3. Данные COROS нового устаревали — закрыто в 0.32.3

В 0.32.3 `coros_mcp` добавлен в `bot._night_services`, `bot._night_ready` и `bot._collect_morning_snapshot`.
Проверка: на следующий день после 09:00 МСК у всех активных пользователей нового COROS дата загрузки
в `raw_service_data` должна быть сегодняшней.

Осталось: `coros_mcp.get_vo2max` по-прежнему читает сохранённый ответ и сам за свежим не ходит.
При работающей ежедневной загрузке это не мешает.

Старый COROS (`coros`) решено убрать отовсюду, отдельной задачей. На 29.09 он подключён у восьми человек,
у пятерых это единственный трекер: uid 6, 17, 20, 27, 117. До удаления им нужно перейти на новую схему.

**Причина, найденная 29.09.** Ночная загрузка идёт только для тех, у кого есть «ночной сервис».
Список задан в `bot._night_services`: `garmin`, `coros`, `polar`, `whoop`. Нового COROS (`coros_mcp`) в нём не было.
Пользователь, у которого подключён только новый COROS, пропускается обеими ночными загрузками
(`scheduled_wakeup_poll` и вторая, рядом). У кого вместе с новым остался старый COROS, Garmin или Whoop,
данные обновляются, потому что загрузка запускается из-за второго сервиса и заодно тянет новый COROS.

На 29.09 только новый COROS у шести пользователей: uid 43, 68, 74, 122, 139, 140. У uid 43, 74, 122 и 139
данные не обновлялись с 17–22.09. uid 139 заблокировал бота. Сроки действия токенов у всех в порядке.

Чтобы исправить, нужно добавить `coros_mcp` в список и в `bot._night_ready` правило, по которому
ночь считается загруженной для нового COROS.
`coros_mcp.get_vo2max` читает сохранённое в `raw_service_data` и за свежим ходит, только если там пусто.
Дата записи при этом ставится текущая. На 29.09 у четырёх пользователей данные были от 17–22.09.

## 12. Как проверить на сервере

Состояние якорей одного пользователя:

```bash
sqlite3 -header -column /opt/running-bot/running_bot.db "SELECT vo2max_device, vo2max_device_source, vo2max_manual, vo2max_manual_note, vo2max_priority, lt_pace_device, lt_device_source, lt_pace_manual, lt_priority FROM user_profile WHERE user_id = 68"
```

Когда и от чего пересчитывались зоны:

```bash
journalctl -u running-bot --since today --no-pager | grep "Зоны пересчитаны для user 68"
```

Ручной запуск кода на сервере: интерпретатор `/opt/running-bot/venv/bin/python`. Файл `.env` содержит
переводы строк Windows, подключать его через `source` напрямую нельзя, сначала убрать символ возврата каретки.
Проверки с записью делать только на копии базы.
