## 🔴 ВЫСОКИЙ ПРИОРИТЕТ

### Онбординг новых пользователей 💡
Главная боль владельца. Высокий барьер входа = отток до того как человек увидит ценность.
- Strava (универсальный вход) недоступна — лимит API=1, заявка на 100 висит, срок неизвестен
- Garmin/COROS требуют логин+пароль — люди боятся
- Навигация в начале неудобная — человек не понимает что делать
Направления:
- Ручной ввод как ПОЛНОЦЕННЫЙ первый класс (пол + результат на дистанции → Риегель → зоны),
  не как fallback. Проверить что путь гладкий
- Снять страх логина честным объяснением (для чего, где хранится, как отключить)
- Онбординг ведёт за руку с первого сообщения: развилка «подключить трекер (точнее) /
  пара вопросов (быстро)», а не вываливание меню
- НЕ завязывать выживание продукта на одобрение Strava
Наблюдение: один юзер подключил COROS ПОСЛЕ утренней рассылки → рекомендация мотивирует
подключаться. Воронка «ценность → подключение» работает.

### Качество рекомендаций — доводка по реальным данным 💡
Формулы сейчас на «разумных дефолтах», откалиброваны по ОДНОМУ забегу владельца (ЛП 4:17).
Тюнить по реальным оценкам (/ratings) и фактам тренировок, когда пойдут данные.
- Крутизну обрыва TTT за порогом дотюнить на замерах с разных людей
- Возможный баг: метка «разгрузочный вариант» появляется на нейтральном восстановлении
  (должна только при плохом recovery) — проверить логику оценки восстановления

## 🟡 СРЕДНИЙ ПРИОРИТЕТ

### Тип длительной — выбор пользователя / лонг на полном ИИ 💡 (07.06.2026)
Сейчас лонг жёстко якорится в easy (аэробный объём) — верно для большинства. Но часть
бегунов осознанно бежит длительную как темповую/прогрессивную работу — им easy занижает.
Направления:
- Опция у пользователя: «восстановительная / аэробная база / темповая длительная».
  Меняет якорь target: восстановительная → ниже easy, база → easy (как сейчас),
  темповая → ближе к марафону. Один флажок, формула читает его как target.
- Перевести лонг на полный ИИ (как интервалы через вариант B) — ИИ сам выбирает группу
  с учётом цели и восстановления, не формула.
- Два запроса: считать оба сценария (база + темповая), показывать/копить статистику.
Контекст: фикс калибровки лонга 07.06 (v0.24.69) убрал округление базы в быструю сторону,
но тип длительной как таковой пока не настраивается.

### Рассылка сообщений от админа 💡 (08.06.2026)
Параметры: когда (сейчас / отложенно), кому (список / условие отбора), текст.
**Этап 1 — «сейчас»** (делаем первым):
- `/broadcast` (админ) → выбор аудитории кнопками → ввод текста → превью с «уйдёт N» → подтверждение → отправка.
- Аудитория переиспользует готовые выборки: `get_active_users`, `get_users_with_service_full`,
  `get_users_with_profile_full`, + «только мне» (тест перед массовой).
- Текст — через `context.user_data["awaiting_broadcast"]` (по образцу фидбэка в `text_handler`).
- Отправка — переиспользовать `_notify_all` (в нём уже цикл + обработка Forbidden → inactive).
  Минимальная правка: `_notify_all` принимает готовый список юзеров опц. аргументом (не только notify_key).
- НЕ плодить дублирующих функций; ничего постороннего не трогать.
**Этап 2 — «отложенно на время»** (потом): нужен планировщик + хранение очереди в БД. Отдельный кусок.

### Вечерняя загрузка фактов тренировки (петля обратной связи) 💡
Вечером после тренировки подтягивать активность из сервиса → как реально прошло.
Замыкает петлю: советовал группу N → факт показывает что держал/добежал/где сдох.
Даёт: проверку рекомендаций, персональную адаптацию (систематически бежит выше/ниже →
запоминать), обновление формы по фактам. Тяжёлый по нагрузке (тянуть .fit/gpx).
ЭТО основной источник данных для калибровки формул.

### FIT-генерация по новой блочной схеме 💡
Вернуть FIT-файл для Garmin (заливка тренировки в часы) + погоду, но генерировать
из новой structure[] (repeat/easy блоки), не через старый генератор. Новая схема
для FIT подходит лучше (явные блоки → чистый repeat-step). Под конкретную группу юзера.

### Составной повтор: несколько рабочих сегментов внутри одного repeat 💡 (08.06.2026)
Проблема: текущая structure[] плоская — repeat-блок = ОДИН work_distance_m + ОДИН
recovery_distance_m. Составной километр («1000 = 800 база + 200 ускорение, отдых 200
после связки», или 600+400 и т.п.) она не выражает: бот держит это одним блоком 8×1000
и сводит 800/200 в прогрессию темпа на километре. Для выбора группы по зонам это «ок»,
но для Garmin-экспорта структура неверная.
Цель (подтверждена реальным Garmin-экспортом, референс лежит в
img/references/garmin_composite_rep_DD_20260609.json): один RepeatGroupDTO
numberOfIterations=8, внутри ПОДРЯД — interval 800 (pace.zone, база) + interval 200
(pace.zone, ускорение) + recovery 200 (no.target), skipLastRestStep=true. У КАЖДОГО
рабочего сегмента свой темп.
План (обратносовместимо, по одному потребителю, НЕ за раз):
- structure[]: добавить опц. поле segments[] у repeat-блока
  ({distance_m, role}); если segments нет — старое поведение (work_distance_m) как сейчас.
  Старые анализы в workout_analysis не ломаются.
- groups[].blocks: темп привязать к сегменту (у каждого segment свой work_pace).
  Это самое тонкое место.
- Промпт Шага 1: правило когда дробить (куски с разными режимами внутри отрезка →
  segments, без отдыха между ними).
- _format_analysis_result: показать сегменты админу.
- recommend_group / _group_primary_pace: определяющий сегмент для зоны.
- fit_generator: генерить связку как несколько interval-шагов внутри одного repeat.
Ждёт оценки частоты: насколько часто у клуба реально такие составные километры —
от этого приоритет. Пока 🟢 если редко, 🟡 если регулярно.

## Анализ факта тренировки — слой s4_activity (зафиксировано 12.06.2026, в РАБОТЕ)

Цель: бот сам разбирает выполненную тренировку против плана. Три фокуса:
(1) выполнение целей по средним на отрезках, (2) ровность темпа внутри отрезка,
(3) пульсовые зоны.

Архитектура: универсальный слой (по образцу unified_cache) — сервис-парсеры
собирают в единый формат, графики/анализ сервиса не знают.

Схема s4_activity (согласована):
  source, activity_id, date, name (DD-маска → workout_date+группа)
  summary: distance_m, duration_s, avg_hr, max_hr, training_load
  hr_zones: [{zone, secs, low_boundary}]
  laps: [{idx, role: work|rest|tail, distance_m, duration_s, avg_pace_s,
          avg_hr, max_hr, wkt_step_index, compliance_score,
          pace_evenness (avg_speed/max_speed)}]
  tail = короткий хвост-добегание (напр. 20м) — не выкидываем и не считаем рабочим.

Источники (порядок): 1) Garmin — 15 юзеров, без лимитов, всё готовое;
2) COROS — 6 юзеров, детали активности искать в соседних эндпоинтах;
3) Strava — лимит 10 атлетов (занято 5), ждём повышения.

Пометка наших тренировок: у каждого сервиса свой способ. Garmin: имя активности
наследует workoutName по маске DD_YYYYMMDD-<группа>_lvl (проверено:
'Москва - DD_20260612-3.5_lvl') — фильтр по вхождению 'DD_'. Разминка/заминка —
отдельные активности, отсеиваются сами.

Факты Garmin API (пробник scripts/probe_garmin_activity.py, 12.06):
- get_activities: сводка с hrTimeInZone_1..5, activityTrainingLoad, lapCount, workoutId
- get_activity_splits: lapDTOs с intensityType (ACTIVE/RECOVERY), wktStepIndex
  (привязка к шагу загруженной тренировки!), directWorkoutComplianceScore
  (Garmin сам считает соответствие), averageSpeed/maxSpeed, HR по лэпу, lengthDTOs
- get_activity_hr_in_timezones: зоны с границами
- для рядов (ровность точнее): get_activity_details — на второй этап

Графики (эталон — ячейки Антона в notebooks/start.ipynb, код в истории чата 12.06):
1) Рабочие интервалы: точки темпов, средние по пятёркам (hlines+звёзды),
   тренд через средние, ЭТАЛОН = плановая прогрессия группы из workout_analysis
   (не руками). Ось Y инвертирована, формат мм:сс.
2) Отдых: точки + два тренда (по всем / по средним) + ЭТАЛОННЫЙ КОРИДОР
   ТОЛЬКО если в плане есть recovery_pace (правило данных: нет плана — нет коридора,
   никаких захардкоженных 5:00-5:30).
Графики рисует бот (matplotlib на сервере) и шлёт картинкой в чат.

Хранение: сырой ответ (activity+splits+zones) → raw_service_data под ключом
'garmin_activity'; нормализованное → по образцу unified_cache (отдельная таблица/ключ).

План шагов: 1) парсер Garmin → s4_activity (скриптом, без бота);
2) привязка к плану (DD-имя → workout_analysis, группа → целевые темпы);
3) два графика по эталону из ноутбука; 4) команда/кнопка в боте; 5) COROS-парсер.
