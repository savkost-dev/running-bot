## Что это
Telegram бот @DoDick_bot для бегового клуба Dusty Dumbbells.
Помогает участникам выбрать группу для тренировки на основе их физической формы.

**Фокус аудитории:** ~30 активных пользователей, которые бегают вт/пт интервальные.
Для них бот — основной сервис. Длительная (вс) — приятное дополнение, облегчённая модель.
Те, кто бегает ТОЛЬКО длительную — не в фокусе. На все ~500 участников клуба не ориентируемся.

**Важный нюанс про рекомендации:** тренер ставит структуру тренировки и распределяет
~10-15 «своих» по группам (их темпы в анонсе — калиброванные опорные точки). ОСТАЛЬНЫЕ
выбирают группу сами. Бот делает рекомендации именно для самостоятельных бегунов,
которых тренер не учитывал.

## === ДВУХШАГОВАЯ ОБРАБОТКА (ядро системы, СДЕЛАНО кроме И3) ===

Раньше: каждый /workout заново парсил анонс из канала — медленно, ненадёжно, формат плыл.
Теперь: анонс анализируется ОДИН раз при выходе → структура в БД → при запросе берётся
готовый анализ + данные пользователя → рекомендация.

### Шаг 1 — Анализ анонса (`analyze_workout` в claude_advisor.py) — СДЕЛАНО
Прод-режим deep. Извлекает структуру, суть, группы, осмысление. Отлажен на реальных анонсах.

**Правила парсинга (выверены на реальных постах):**
- Формат времени: точка = разделитель мин:сек. "1.32" = 1 мин 32 сек. Целое без точки = секунды
- Работа vs восстановление когда оба заданы временем: длиннее/быстрее = work, короче/медленнее = recovery
- active_recovery (логика OR): true если ЛИБО темп быстрее 5:30/км, ЛИБО медленнее работы не более ~50%.
  Нет целевого темпа → active_recovery=false, не фантазировать
- Группа здоровья/ходоков (⏺️ или "бег и ходьба"): ловить по СМЫСЛУ (может быть с номером или без),
  health_group=true, темп не выдумывать. Используется для новичков и пустых профилей
- Доп. группа со ссылкой ("3.5 работает с группой 3") → в extra_groups, без выдуманных отрезков
- Доп. группа с ПОЛНЫМ набором отрезков (группа 5) → в основной groups с from_comment=true
- Группа 5 часто бегает по 4-й дорожке → нестандартные дистанции (322/430/108м) это НОРМА
- Единая структура: задаётся раз, все группы делают одно, отличаются темпом (иногда числом повторов)
- Орг-инфа (перенос места на будущее, регистрация, чаты, MAX) → в ignored
- Индивидуальные советы с датами забегов → в ignored (не в coach_notes)

**JSON-схема (interval):** structure[] (блоки типа repeat/easy с purpose), overall_purpose,
total_volume_km, is_borderline + borderline_note, поля осмысления (block_contrast,
target_athlete, intensity_level, what_to_watch), groups[] (только темпы по блокам + reps_override
+ from_comment + track_note + health_group), extra_groups[], coach_notes, ignored.

**JSON-схема (long):** проще. duration_min, warmup, cooldown, route_note, has_progression,
groups[] (start_pace + target_pace + health_group). is_borderline почти всегда false.
- Прогрессия фиксированная: вторая половина на 30 сек/км быстрее. Если конечный темп не указан
  (даже у группы 1) → target = start −30 сек/км. Группа 1: 4:30 → 4:00
- Ровный темп доступен ВСЕГДА (база), прогрессия — опция поверх. Звёздочки не разбираем
- Принцип для long: формат стабилен годами, ДОСТРАИВАТЬ пропущенное по стандарту клуба

### Шаг 2 — Рекомендация — СДЕЛАНО (recommend_group / recommend_long), интеграция = И3 (TODO)

**Персональные зоны (zones.py):** считаются от лактатного порога (приоритет) → VO2max → Риегель.
Подход Дэниелса. Хранятся в athlete_cache (pace_zones_json, zones_source, zones_updated_at).
Пересчёт: ночной refresh + ручной ввод ЛП/VO2max + при подключении трекера. НЕ при смене специализации.
Зоны — свойство ЧЕЛОВЕКА, не тренировки.

**recommend_group (interval) — целевая функция «интеграл интенсивности по времени»:**
Итоговый % = полезность_зоны × quality_volume.
- quality_volume = intensity(pace) × time_to_termination(pace, recovery), нормировано к пику
- time_to_termination: плато ниже порога, РЕЗКИЙ нелинейный обрыв выше порога (накопление лактата),
  поправка на восстановление. Формула 1/(1+(Δ/τ)^k)
- Максимум кривой — у порога с лёгким заходом выше = оптимум (и развивает, и дотягиваешь)
- Слишком быстро (гр.1) → обрыв (мало времени работы, риск схода). Слишком медленно (гр.5) →
  нет интенсивности (низкий стимул). Развивающее окно с двух сторон
- Полезность зоны зависит от ХАРАКТЕРА тренировки (overall_purpose), не только специализации:
  на скоростной даже полумарафонцу ценнее МПК/скорость (ПАНО добирается в другие дни)
- is_borderline=false → основная группа по ЧИСТОЙ форме (специализация не влияет,
  вес спец перенормируется в форму/восстановление)
- Константы вынесены: _USEFULNESS_FLOOR=0.80, _INTENSITY_EXP=4, _TTT_TAU=28, _TTT_STEEP=3.8,
  _TTT_RECOVERY_K=0.35, веса non-borderline _W_FORM_NB/_W_REC_NB=0.58/0.42
  (+ таблицы _SPEC_ZONE_VALUE / _CHARACTER_ZONE) — для калибровки по /ratings и фактам

**Калибровка-эталон (профиль ЛП 4:17, нейтральное восстановление), проверено на реальном забеге:**
гр1≈10% (риск схода), гр2≈68% (тяжело но реально), гр3≈90% (оптимум), гр4≈60% (низкий стимул/
разгрузочный), гр5≈40% (низкий стимул). При плохом восстановлении грань отказа ближе, гр2 падает,
гр4 поднимается как разгрузочная.

**recommend_long — облегчённая модель (детерминированная, 0 токенов):**
По форме → базовая группа + 1-2 соседних (выше = темповая/die-hard, ниже = спокойнее/здоровье).
Упомянуть прогрессию (опция) и ровный темп (норма). Тон проще, акцент «потянешь ли 100 мин».
Пустой профиль → консервативный ориентир + активно предложить группу здоровья новичкам.
Специализация для long почти не влияет.

### ⚠️ ОНБОРДИНГ И ПОСТАВЩИКИ ДАННЫХ — узкое место, ВОЛНУЕТ ВЛАДЕЛЬЦА
Это конкурирует по важности с И3: И3 улучшает рекомендацию для тех, кто УЖЕ внутри,
а онбординг определяет, сколько людей вообще дойдут до рекомендации. С учётом оттока —
возможно приоритетнее. Человек должен с ПЕРВОЙ минуты понять что делать.

Текущая боль — у нового человека выбор между «недоступно» и «страшно»:
- **Strava** задумывалась как УНИВЕРСАЛЬНЫЙ вход (OAuth, не пугает, тянет данные включая
  Apple Health). НО: лимит API = 1 пользователь (сейчас только владелец). Заявка на 100
  подана, висит. Процесс Strava печально медленный/непредсказуемый (форумы разработчиков
  полны жалоб). Срок одобрения неизвестен.
- **Garmin / COROS** работают, но через логин+пароль — люди боятся вводить (психологически
  тяжело отдавать пароль от аккаунта стороннему боту).
- Навигация в начале была не очень удобная.

Направления (обсуждать, не задание):
1. Пока Strava не одобрена — РУЧНОЙ ВВОД должен быть полноценным первым классом, не fallback.
   Минимум: пол + результат на дистанции (Риегель → зоны) ИЛИ ЛП. Путь от Риегеля заложен —
   убедиться что он гладкий и подаётся как нормальный вариант, а не «ну ладно, введи руками».
2. Снять страх логин/пароля честным объяснением в момент подключения (для чего, где хранится,
   как отключить). Прозрачность снижает страх.
3. Онбординг с первого сообщения ведёт за руку: не вываливать меню, а развилка с понятными
   последствиями — «подключить трекер (точнее) ИЛИ пара вопросов (быстро)».
4. НЕ завязывать выживание продукта на одобрение Strava. Продукт полезен и без неё
   (ручной путь + Garmin/COROS для смелых = рабочий минимум). Strava когда откроется —
   бонус (универсальный вход, Apple Health), а не условие.

### Apple Health — отложено
HealthKit даёт VO2max, но только через iOS-приложение, не через бота напрямую. Нужен
промежуточный сервис (Strava тянет из Apple Health) или отдельное мобильное приложение.
